NEW -- concrete endpoint, not just a hypothetical shape -- the real-mode client now calls a
specific mark-as-read endpoint on dismiss:

 POST /notifications/{id}/read -- src/services/notifications.js:278

The reference document's §14 only speculated "a PATCH /notifications/{id}/read-style mechanism will
be needed." The frontend has since committed to a concrete verb and path: POST, not PATCH. The main
listing endpoint ( GET /notifications ) is still unbuilt server-side -- unchanged from the reference
document.

NEW -- "Mark all as read" ( pages/notifications.jsx ) does not call a bulk endpoint. It loops over
every visible item and fires the same POST /notifications/{id}/read call once per item
( src/pages/notifications.jsx:76-83 ). If a volunteer/organization has many unseen notifications, this
means N parallel POST requests, not one. Worth a bulk POST /notifications/read-all if the backend
team wants to avoid that, but it is not required by the current frontend contract.

UPDATE (2026-08-14) -- client-side unread filtering added; a real bug in the real-mode branch is
now fixed. Previously the real-mode client read a seen field back from the (still hypothetical) GET
/notifications response but never actually used it to filter -- every notification the backend ever
returned, read or unread, would have counted toward the bell badge and appeared in the dropdown.

    sends ?unread=true optimistically on GET /notifications (mirrors the same optimistic-query-

     src/services/organizations.js:205 ), and
    defensively filters out any item with seen: true client-side regardless of whether the backend
    honors that param ( data.filter((item) => !item.seen) ), so the returned list is guaranteed
    unread-only either way -- matching the mock-mode branch's existing behavior of only ever
    returning unseen items.

 src/services/notifications.js:258-282

§17.4 Applicants list -- new required field: volunteer.email

UPDATE (2026-08-14) -- the applicant card and the volunteer profile preview modal (both reached
from the organization's "Applicants" page) now display the volunteer's email address next to their
phone number, using the same treatment already given to volunteer.phone and volunteer.photo in
this same response: read directly off the nested volunteer object, rendered only when present, no
separate lookup call.

Why: organizations reviewing applicants currently only see a phone number as a contact method. Email
is a second, equally direct contact channel, and every volunteer account already has one (it's the login
identifier, §3.1 of the reference document) -- so no new data collection is required, only exposing a
field that already exists on the user record.

Exact field name: email , nested inside the volunteer object of each item in the GET
/opportunities/{id}/participants response -- i.e. volunteer.email , sibling to the already-
documented volunteer.phone and volunteer.photo fields (§16 of the reference document), not a
top-level field on the participation record itself.

   Backend action: add email to the nested volunteer object returned by GET
   /opportunities/{id}/participants (sourced from users.email for that participation's
   volunteer). No renaming, no normalization layer, and no new frontend logic is involved on this
   side -- src/services/participations.js was deliberately left untouched; the field is expected
   to arrive already shaped inside the nested volunteer object, exactly like volunteer.phone does
   today. If the field is absent or empty, the frontend simply omits the row (same defensive pattern
   already used for volunteer.city and volunteer.phone ) -- so this is safe to ship incrementally
   and won't break anything if rolled out before the rest of the participants endpoint is finished.
