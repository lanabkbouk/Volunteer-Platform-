      1. Tech Stack Context

        React 19 + Vite 8, React Router v7 (data router), TanStack React Query v5, React Hook Form + Zod v4, Axios, Tailwind v4. No Redux
        -- global state is a single AuthContext (session only) plus React Query for all server data. ( package.json )
        The app runs in two modes controlled by one env var: VITE_API_MODE=real hits the live Laravel API; anything else (including
        unset) uses an in-memory/localStorage mock layer that mirrors the intended real contract ( src/services/api/mockMode.js:12-
        14 ). Every service function branches on this flag, so the mock code is effectively executable documentation of the intended
        API contract -- it is the primary source for the request/response shapes in this document.

      2. Global API Conventions

        All requests go through one Axios instance ( src/services/api/client.js ):
             Base URL: VITE_API_BASE_URL env var ( client.js:5 ).
             Auth header: every request reads localStorage['auth_session'] , parses it, and if .token is a non-empty string, sets
              Authorization: Bearer {token} ( client.js:13-27 ). The frontend never manages the token in memory/state -- it re-
             reads storage per request.
             Response envelope: if a response body is a non-array object with a data key (Laravel API Resource shape {data, meta?,
             links?} ), the client unwraps it -- response.data becomes the inner data , and meta / links are hoisted onto the
             response ( client.js:29-45 ). Every endpoint should either return a bare JSON body, or this Resource envelope -- not
             something else.
             401 handling: any 401 response clears the stored session and hard-redirects to /login (loop-guarded) ( client.js:50-
             64 ). No refresh-token flow exists anywhere in the codebase.

Error contract expected:

     All other errors: a top-level message or error string ( client.js:66-74 , getApiErrorMessage ).

Service-layer return shape (frontend-internal, not literally what Laravel must return): every service function normalizes both
mock and real results into { success: boolean, data?, error?, fieldErrors? } before handing it to a hook/component.
This means the backend does not need to literally return success: true -- the frontend derives it from HTTP status/axios
success -- but it does mean every mutation's success response should include the created/updated resource in the body
so the frontend can populate data .
File uploads / updates: any endpoint that both accepts a file and is a resource update must accept POST with a spoofed
method -- FormData.append('_method', 'PUT') -- because PHP cannot parse $_FILES on a true PUT multipart request
( src/services/api/mediaUpload.js:29-41 , confirmed pattern reused in opportunities.js , volunteer.js ,
organization.js ).

18. React Query / Data Synchronization Requirements

     Global cache defaults: staleTime: 60s , retry: 1 , refetchOnWindowFocus: false ( src/app/queryClient.js ).

     Query key hierarchy is resource-rooted ( src/app/queryKeys.js ) -- e.g. opportunities.all is a prefix that, when
     invalidated, implicitly invalidates list/suggested/detail/mine/completed . Every opportunity mutation
     (create/update/delete/toggle-status/participate) is expected to affect all of these views consistently -- i.e. read-after-
     write consistency on a single opportunities resource.

     Mutations widely assume the response body includes the created/updated resource (used to patch the cache directly via
      setQueryData ) -- e.g. category/skill/city create-mutations expect result.data to be the new object; the city update-
     mutation matches the cache entry by result.data.id , implying the response's id must equal the requested resource's
     id.

     Skills responses must embed a full nested category object, not just a categoryId -- confirmed by frontend

     comments explaining why skill mutations use full-list invalidation instead of optimistic patching (rebuilding the nested object
     client-side was judged not worth it) ( useCreateSkillMutation.js / useUpdateSkillMutation.js comments).

     Contract inconsistency to resolve: useReviewOrganizationMutation reads result.status / result.reason at the top

     level of the mutation response, while every other mutation in the codebase reads result.data.{...} . Recommend
     standardizing before backend implementation.
     Polling: only one hook polls on an interval -- useRecentUpdates at 5 seconds (§14). All other data hooks rely on cache
     invalidation/refetch-on-navigation, not polling. No websockets/SSE anywhere.

21. Business Rules the Backend Must Enforce

  1. Opportunity status is always derived from dates/counts, never manually set except the registrationClosedManually toggle
     (§7.2).

  2. current_volu is a live count of accepted participations -- never a stored increment/decrement counter (§3.4).
  3. A volunteer cannot have two simultaneously active ( pending / accepted ) participations for the same opportunity; re-

     applying after rejected / withdrawn is explicitly allowed.
  4. Withdrawal is only valid while the opportunity's registration is still open -- not gated by the opportunity's start date directly.
  5. Rejecting or suspending an organization requires a non-empty reason ; approving does not.
  6. Resubmitting a verification document must reset an organization's status to pending and clear its rejection reason server-

     side.
  7. Achievement unlocking must be computed and persisted entirely server-side (event/observer-driven on participation

     completion) -- never admin-set, never frontend-computed in production.
  8. Anti-enumeration: forgot-password must always return a generic success response regardless of whether the email exists.
  9. Password reset tokens should be single-use and time-limited (mock mirrors Laravel's ~1 hour default).
10. File-upload update endpoints must accept POST + _method=PUT override (PHP cannot parse multipart on true PUT ).
11. Withdrawn participations must never be hard-deleted -- kept as status = withdrawn , distinct from rejected , to preserve

     a transparent history for both volunteer and organization.
